# OpenX32 DSP Build Guide (Linux/Wine)

Build DSP1 and DSP2 SHARC firmware reproducibly on Linux using CCES 2.12.1 under Wine.

## Prerequisites

| Component | Version | Notes |
|-----------|---------|-------|
| Wine | 11.x (tested with 11.17) | `wine --version` |
| CCES | 2.12.1 | CrossCore Embedded Studio |
| SHARC compiler | 8.16.1.0 | Bundled with CCES 2.12.1 |
| sha256sum | any | Part of coreutils |

## CCES Installation

1. Download **CrossCore Embedded Studio 2.12.1** from [Analog Devices](https://www.analog.com/cces).
2. Install under Wine:
   ```bash
   wine CCES-Win-x86-2.12.1.exe
   ```
   Accept the default install path: `C:\Analog Devices\CrossCore Embedded Studio 2.12.1`

3. **Licensing**: CCES requires a valid license. Place your license file as
   directed by the Analog Devices license manager, or set the `LM_LICENSE_FILE`
   environment variable before building.

## One-Time Wine Setup

The build script (`build-dsp.sh`) handles these automatically on first run,
but for reference the required compatibility links are:

| Link | Target | Reason |
|------|--------|--------|
| `C:\Programme2\AnalogDevices\CCES2` | CCES install dir | DSP2 `.cproject` uses this legacy path for the kernel loader |
| `CCES_HOME/System/SHARC` | `CCES_HOME/SHARC` | Headless tools resolve include paths via `System/SHARC/` |
| `C:\windows\increaseVersion.bat` | (no-op shim) | Pre-build step; the shim preserves `version.h` for reproducible builds |

The script creates these idempotently — they are safe to re-run.

## Building

```bash
# Build both DSP1 and DSP2 (default)
./dsp/build-dsp.sh

# Build a single target
./dsp/build-dsp.sh dsp1

# Custom output directory
./dsp/build-dsp.sh --output-dir=/tmp/my-dsp-build all
```

### Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `CCES_HOME` | `~/.wine/drive_c/Analog Devices/CrossCore Embedded Studio 2.12.1` | CCES installation path inside the Wine prefix |

## Output Files

After a successful build, the output directory contains:

| File | Description | Deterministic? |
|------|-------------|----------------|
| `dspN.ldr` | Boot loader image (SPI flash binary) | ✅ Yes — **primary reproducibility artifact** |
| `dspN.dxe` | Linked SHARC executable (ELF) | ⚠️ No — contains a random `link-project-guid` |
| `dspN.map.xml` | Linker memory map | ⚠️ No — contains GUID and heap pointer IDs |
| `dspN_linker_log.xml` | Linker diagnostic log | ❌ Contains timestamps and pointer IDs |
| `dspN_build.log` | Full build console output | ❌ Contains timestamps |
| `sha256sums.txt` | SHA-256 of LDR files only | — |
| `sha256sums_all.txt` | SHA-256 of all artifacts | — |

### DXE Non-Determinism

The SHARC linker (`cc21k`) embeds a random `link-project-guid` in every DXE
it produces. This GUID also appears in `map.xml` and `linker_log.xml`. The
GUID is metadata only — the actual executable code and data are identical
across builds. The LDR loader image (`elfloader`) strips this metadata, so
**LDR files are bit-for-bit reproducible** and are used for checksum
verification.

## Comparing with a Baseline

```bash
# Compare LDR checksums (deterministic) against a known-good baseline
diff <(cat /tmp/my-dsp-build/sha256sums.txt | sort) \
     <(grep '\.ldr$' /tmp/openx32-dsp-baseline/sha256sums.txt | sort)

# Or verify file-by-file
sha256sum -c /tmp/my-dsp-build/sha256sums.txt
```

If LDR checksums match, the build is reproducible — the firmware binaries
that get flashed to the DSP hardware are identical.

To inspect DXE differences (expected to be only the `link-project-guid`):
```bash
cmp -l baseline.dxe new.dxe  # should show ~15 differing bytes
```

## Common Failures

### `make: *** No rule to make target 'clean'. Stop.`
This is **normal** — it appears during the clean phase of `-cleanBuild` when
the Release directory has no generated makefiles yet. CCES retries and the
build proceeds. Check for `PASSED` in the build log.

### `Error 1 (ignored)` in post-build
The `CCES_MMV.exe` post-build step opens a GUI memory-map viewer. With
`DISPLAY=""` (set by the build script), it cannot open a window and exits
with error. This is intentionally ignored — the `map.xml` is generated by
the linker, not by MMV. The dash prefix (`-CCES_MMV.exe`) in the makefile
tells make to ignore the error.

### `increaseVersion.bat` not found
The build script installs a no-op shim in `C:\windows`. If you see this
error, check that the Wine prefix is writable:
```bash
ls -la ~/.wine/drive_c/windows/increaseVersion.bat
```

### License errors
If the build log contains license-related errors, ensure your CCES license
is valid and accessible. Set `LM_LICENSE_FILE` if needed.

### Wine `fixme:` messages
Wine prints many `fixme:` debug messages to stderr. These are captured in
the build log and are harmless.

## CCES_MMV.exe (Memory Map Viewer)

The `.cproject` post-build step runs `CCES_MMV.exe <target>.map.xml` to
display a memory-map visualization. This is a GUI application that cannot
run headlessly.

The build script sets `DISPLAY=""` to prevent it from opening a window.
The `map.xml` file is produced by the linker (`cc21k -map`), **not** by MMV,
so this has no effect on build artifacts.

If you want MMV screenshots (as in the baseline build), you need:
- A running X server or Xvfb virtual framebuffer
- `xdotool` to detect and close the MMV window
- `import` (ImageMagick) to capture screenshots

This is not needed for reproducible builds.

## Machine-Specific Assumptions

- Wine prefix at `~/.wine` (standard default)
- CCES installed at the default Windows path
- The repository is accessible via Wine's Z: drive mapping (default: maps `/` to `Z:`)
- `version.h` files are not modified locally (tracked in git)
